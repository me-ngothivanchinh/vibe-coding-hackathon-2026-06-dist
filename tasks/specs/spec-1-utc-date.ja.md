# 仕様例: #1 議事録の日付がズレて表示される

> 言語: [English](spec-1-utc-date.md) | **日本語** | [Tiếng Việt](spec-1-utc-date.vi.md)

> これは「一例」です。合理的な別解釈で実装しても問題ありません。
> 受け入れ基準を満たすこと、なぜそう実装したかを説明できることが重要です。

## 受け入れ基準

1. **JST (Asia/Tokyo, UTC+9) で会議が行われた日付** が、一覧画面と詳細画面の両方で表示される
2. JST 0:00 〜 9:00 に作成された会議でも、表示日付がズレない
3. ブラウザのタイムゾーン設定に依らず、常に JST で表示される（このアプリは JST 拠点利用が前提）
4. 既存の議事録データ（DB に保存されている `meetingDate`）はそのまま使える状態であること（マイグレーション不要）

## 想定される実装の方向性

問題の根本: 現状の表示処理では、UTC のまま日付部分を切り出しているため、UTC 日付と JST 日付がズレるレコードでズレた日付が表示される。

修正の方向（どれを採用してもよい、別解も可）:

- **A. 表示時に明示的に Asia/Tokyo タイムゾーンで整形する**
  - `Intl.DateTimeFormat('ja-JP', { timeZone: 'Asia/Tokyo', ... })` を使う
  - もしくは `date-fns-tz` / `dayjs` などのライブラリで明示的に変換
- **B. 文字列操作ではなく Date オブジェクトのローカル時刻メソッドを使う**
  - ただしブラウザ TZ に依存するので推奨しない
- **C. API 側で表示用文字列を返す**
  - 過剰実装気味、A で十分

推奨: **A**。最小修正は表示ユーティリティ関数（`formatDate`）の中だけ。

## 確認方法（参加者向け）

修正後、以下のシナリオで確認:

1. 新規作成画面で日付を「2026-06-01」に設定し、保存
2. 一覧画面で「2026-06-01」と表示されることを確認
3. ブラウザの開発者ツールで時刻を「2026-06-01 07:00 JST」相当に変更しても表示は変わらないこと
4. 既存の seed データ（朝の時間帯の会議があれば）も JST 日付で表示されていること

## 評価ポイント（参加者にも事前共有可、別文書）

- タイムゾーン対応の意図を理解しているか（UTC vs JST の概念）
- 修正範囲が最小か（DB 変更や API 変更まで広げていないか）
- AI ツールに丸投げした場合でも、最低限の動作確認をしているか

## 補足

- 「既存データを書き換える」マイグレーションは不要です。データ自体は正しく保存されています。表示処理だけの修正で完結するはずです。
- 詳細画面・編集画面で時刻部分（時:分）を出すかどうかは別判断。本仕様では「日付」の表示が正しければ OK。
